# Quartz 블로그 자동 배포 워크플로우

로컬에서 `git push` 한 번이면 GitHub이 알아서 빌드하고 사이트를 갱신합니다. 그 사이에 무슨 일이 일어나는지, 문제가 생기면 어디를 봐야 하는지 정리한 문서입니다.

---

## 1. 전체 흐름

```
[내 맥북]                      [GitHub]                        [인터넷]

Obsidian으로 글 작성
   ↓
content/글.md 저장
   ↓
git push origin main  ────→  push 이벤트 감지
                                 ↓
                             Actions 실행
                             ├ 저장소 체크아웃 (전체 히스토리)
                             ├ Node 22 설치
                             ├ npm ci
                             ├ npx quartz plugin install
                             ├ npx quartz build   → public/ 생성
                             └ public/ 을 artifact로 업로드
                                 ↓
                             deploy 잡
                             └ GitHub Pages에 배포  ────→  https://계정.github.io
```

빌드는 GitHub의 우분투 러너에서 돌기 때문에 **내 컴퓨터가 꺼져 있어도 무관**합니다. 평균 1~3분 소요.

---

## 2. 워크플로 파일

`.github/workflows/deploy-pages.yaml`

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install dependencies
        run: npm ci

      - name: Install Quartz plugins
        run: npx quartz plugin install

      - name: Build Quartz
        run: npx quartz build

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: public

  deploy:
    needs: build
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

---

## 3. 각 설정이 하는 일

### 트리거

| 설정 | 의미 |
|---|---|
| `on: push: branches: [main]` | `main` 브랜치에 push될 때만 실행. 다른 브랜치 작업은 배포되지 않음 |
| `workflow_dispatch` | Actions 탭에서 **Run workflow** 버튼으로 수동 실행 가능 |

`workflow_dispatch`는 없어도 배포는 되지만, 배포만 다시 돌리고 싶을 때(설정 변경 후 등) 유용하므로 넣어두는 편이 좋습니다.

### 권한

| 권한 | 필요한 이유 |
|---|---|
| `contents: read` | 저장소 소스를 체크아웃 |
| `pages: write` | GitHub Pages에 배포 |
| `id-token: write` | Pages 배포 시 OIDC 인증 토큰 발급 |

세 개 중 하나라도 빠지면 deploy 단계에서 권한 오류가 납니다. 별도의 시크릿(Secrets)은 필요 없습니다 — `GITHUB_TOKEN`이 자동으로 주입됩니다.

### 동시 실행 제어

```yaml
concurrency:
  group: pages
  cancel-in-progress: false
```

연달아 push했을 때 배포가 겹치는 것을 막습니다. `cancel-in-progress: false`라 앞선 배포를 취소하지 않고 순서대로 끝냅니다. `true`로 두면 마지막 push만 배포되어 더 빠르지만, 중간 배포가 취소됩니다.

### 빌드 단계

| 단계 | 하는 일 | 주의점 |
|---|---|---|
| `checkout@v4` + `fetch-depth: 0` | 소스와 **전체 git 히스토리**를 가져옴 | 이 옵션이 없으면 글 작성일이 전부 "오늘"로 표시됨 |
| `setup-node@v4` | Node 22 설치 | `.node-version` 파일과 버전이 맞아야 함 |
| `npm ci` | `package-lock.json` 기준으로 정확히 설치 | `npm install`이 아니라 `ci` — 락 파일과 어긋나면 실패시켜 문제를 조기에 드러냄 |
| `npx quartz plugin install` | 추가 설치한 커뮤니티 플러그인 복원 | 플러그인을 안 썼으면 경고만 뜨고 통과 |
| `npx quartz build` | `content/` → `public/` 정적 사이트 생성 | 여기서 실패하면 대개 마크다운 문법 또는 설정 오류 |
| `upload-pages-artifact@v3` | `public/` 폴더를 배포용 아티팩트로 압축 | `path`가 `public`이어야 함 |

### 배포 단계

`needs: build`라서 빌드가 성공해야만 실행됩니다. `environment.url`은 배포 완료 후 Actions 화면에 사이트 링크를 띄워주는 용도입니다.

---

## 4. 왜 `fetch-depth: 0`인가

Quartz의 `created-modified-date` 플러그인은 글의 날짜를 이 순서로 찾습니다.

1. frontmatter의 `date` 값
2. **git 커밋 기록**
3. 파일시스템 타임스탬프

기본 체크아웃은 최근 커밋 1개만 가져오므로(shallow clone) git 기록이 없습니다. 그러면 3번으로 넘어가 모든 글이 빌드 시각으로 표시됩니다. `fetch-depth: 0`은 전체 히스토리를 가져와 2번이 동작하게 합니다.

`date`를 항상 직접 적는다면 없어도 되지만, 남겨두는 쪽이 안전합니다.

---

## 5. 사전 설정 (한 번만)

워크플로 파일만 있어서는 동작하지 않습니다. 저장소 설정 세 곳을 맞춰야 합니다.

1. **Settings → Actions → General**
   Actions permissions → `Allow all actions and reusable workflows` → Save
2. **Settings → Pages**
   Source → **GitHub Actions** (`Deploy from a branch`가 아님)
3. **Settings → Environments → github-pages**
   Deployment branches and tags에 `main`이 허용되어 있는지 확인 (예전 브랜치만 허용된 상태면 배포가 거부됨)

## 6. 평소 글쓰기 루틴

```bash
# 1. 글 작성 — Obsidian 또는 에디터로 content/ 안에 .md 추가

# 2. 로컬 확인
npx quartz build --serve
# http://localhost:8080 — 저장하면 자동 새로고침

# 3. 배포
npx quartz sync
```

`npx quartz sync`는 `git add` + `commit` + `push`를 한 번에 처리합니다. 커밋 메시지를 직접 쓰고 싶으면 평소처럼:

```bash
git add .
git commit -m "새 글: 제목"
git push
```

push 후 Actions 탭에서 진행 상황을 볼 수 있고, 초록불이 뜨면 사이트에 반영됩니다.

## 7. 실패했을 때 점검 순서

Actions 탭에서 빨간 X를 클릭하면 어느 단계에서 멈췄는지 보입니다. 단계별로 원인이 다릅니다.

### `npm ci` 실패

`package-lock.json`이 `package.json`과 어긋난 경우입니다. 로컬에서 아래를 실행하고 락 파일을 커밋하세요.

```bash
npm install
git add package-lock.json && git commit -m "락 파일 갱신" && git push
```

### `npx quartz build` 실패

로그의 마지막 몇 줄에 파일명이 찍힙니다. 흔한 원인:

- frontmatter YAML 문법 오류 (콜론 뒤 공백 누락, 따옴표 짝 안 맞음)
- 존재하지 않는 노트를 임베드 (`![[없는노트]]`)
- 이미지 경로 오타

로컬에서 `npx quartz build`를 돌려보면 같은 에러가 그대로 재현됩니다.

### deploy 단계 실패

| 메시지 | 조치 |
|---|---|
| `not allowed to deploy to github-pages due to environment protection rules` | Settings → Environments → github-pages에서 `main` 허용 |
| `Resource not accessible by integration` | `permissions` 블록의 세 항목이 모두 있는지 확인 |
| `Get Pages site failed` | Settings → Pages의 Source가 **GitHub Actions**인지 확인 |

### 워크플로가 아예 실행되지 않음

- Actions가 저장소에서 꺼져 있음 → Settings → Actions → General
- push한 브랜치가 `main`이 아님 → `git branch --show-current`로 확인
- 기본 브랜치가 다른 브랜치임 → Settings → General → Default branch를 ⇄로 전환

### 배포는 성공했는데 사이트가 이상함

빌드는 통과했으므로 설정 문제입니다. `quartz.config.yaml`의 `baseUrl`이 실제 접속 주소와 정확히 같은지 확인하세요 (`https://` 없이). 프로젝트 저장소라면 `계정.github.io/저장소명`처럼 경로까지 포함해야 합니다.

## 8. 더 붙일 수 있는 자동화

필요해지면 추가하는 선택 항목들입니다.

### 예약 발행

특정 시각에 자동 배포하려면 cron 트리거를 추가합니다.

```yaml
on:
  push:
    branches: [main]
  schedule:
    - cron: "0 0 * * *"   # 매일 UTC 00:00 = 한국시간 09:00
  workflow_dispatch:
```

미리 써둔 글의 frontmatter에서 `draft: true`를 지우는 커밋을 예약하는 식으로 활용합니다. cron은 UTC 기준이라 한국시간에서 9시간을 빼야 합니다.

### PR 미리보기 빌드

`main`에 합치기 전에 빌드가 깨지는지 먼저 확인합니다.

```yaml
on:
  pull_request:
    branches: [main]
```

빌드만 돌리고 배포는 하지 않도록 `deploy` 잡에 조건을 겁니다.

```yaml
  deploy:
    if: github.event_name != 'pull_request'
```

### 깨진 링크 검사

빌드 로그에 존재하지 않는 노트로 향하는 링크가 경고로 남습니다. 이걸 실패로 취급하고 싶다면 build 단계를 다음으로 바꿉니다.

```yaml
      - name: Build Quartz
        run: npx quartz build --strict
```

초반에는 경고가 많이 나올 수 있으니 링크를 정리한 뒤에 켜는 편이 낫습니다.

### 별도 vault에서 content 동기화

Obsidian vault를 블로그 저장소 밖에 두고 있다면, 발행할 노트만 골라 복사하는 스크립트를 push 전에 돌립니다.

```bash
#!/bin/bash
# sync-vault.sh — vault에서 publish 표시된 글만 content/로 복사
VAULT="$HOME/Documents/ObsidianVault"
DEST="$HOME/dev/github.com/계정/quartz/content"

rsync -av --delete \
  --include="*/" \
  --include="*.md" \
  --include="*.png" --include="*.jpg" \
  --exclude="*" \
  --exclude=".obsidian/" \
  --exclude="private/" \
  "$VAULT/publish/" "$DEST/"
```

`chmod +x sync-vault.sh` 후 `./sync-vault.sh && npx quartz sync`로 이어 붙이면 한 줄로 발행됩니다. 심볼릭 링크(symlink)로 연결하는 방법도 있지만 GitHub Actions에서는 링크가 풀리지 않으므로, 실제 파일이 복사되는 이 방식이 안전합니다.

## 9. 요약

| 항목 | 값 |
|---|---|
| 트리거 | `main` 브랜치 push, 또는 수동 실행 |
| 빌드 환경 | ubuntu-latest, Node 22 |
| 빌드 산출물 | `public/` |
| 소요 시간 | 약 1~3분 |
| 필요한 시크릿 | 없음 |
| 비용 | 공개 저장소는 무료 (Actions 무제한) |
| 실패 확인 위치 | 저장소 → Actions 탭 |
