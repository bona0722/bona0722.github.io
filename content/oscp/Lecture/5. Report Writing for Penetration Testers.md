침투테스트는 스크립트를 미리 작성할 수 없다.
> 테스트하기를 원하는 시스템이나 네트워크의 종류 예측 불가
> 고객과의 사전 미팅에서 세부 범위를 정의하는 것이 권장됨.

- 진행하면서 메모를 하여 어떤 일이 일어났는지 기록 확인
	- 모든 명령, 수정하는 모든 코드 줄, GUI에서 클릭하는 모든 위치가 기록되어야 작업을 재현할 수 있음
	- 메모를 많이 했다 하더라도, 나중에 살펴보는 것이 평가 중 발생할 일을 정확하게 기억할 수 있도록 모호하지 말아야하며, 구조화 되고 상세해야 함.
	- 노트에 충분한 기술 세부 정보 제공 필요
	- 일관되게 내용 작성해서 다른 사람이 테스트를 반복하여 동일한 결과를 얻을 수 있도록 하기

메모 예시
- 애플리케이션 이름
- URL
- Request Type: GET, POST, OPTIONS 등
- Issue Detail: 취약점이 있는 경우 이를 설명하는 CVE를 가리키거나 관찰한 영향 설명. 서비스 거부, 원격 코드 실행, 권한 상승 등으로 분류 가능
- Proof of Concept Payload: 취약점을 트리거하는 문자열 또는 코드 블록. 문제를 해결하고 재현할 수 있도록 하는 메모의 가장 중요한 부분. 필요한 모든 전제 조건을 나열하고 취약점 다시 트리거할 때 사용해야 하는 정확한 코드나 명령 제공 필요


도구 추천
- 메모
	- Subline: 구문 강조에 좋음
	- CherryTree: Kali에서 제공
	- Obsidian: 마크다운 편집기. 메모 작성에 필요한 모든 기능 포함
- 캡처
	- MAC OS: Shift/Command 조합과 숫자키 3,4,5로 가능. 전체 화면 선택 후 저장하려면 F+B+3. 화면의 특정 영역을 강조 표시하고 선택하려면 F+B+4나 F+B+5
	- Flameshot: OS에 구애받지 않음


고객을 위한 보고서?
- 보고서의 목적
- 우리가 수집한 정보를 청중이 이해할 수 있는 방식으로 전달할 수 있는 방법
회사가 침투 테스터를 고용하는 이유는 무엇입니까? 최종 목표는 서비스 범위 내에서 현재 시스템에 존재하는 모든 결함을 설명하고 강조하는 앞으로의 경로, 이러한 결함을 즉시 수정하는 방법, 그리고 향후 이러한 취약점이 나타나지 않도록 방지할 전략적 목표를 제시하는 것입니다. 이 결과는 침투 테스트 보고서 형식으로 제공되는 경우가 많습니다. 고객의 입장에서 보고서는 (보통) 진정으로 중요한 업무의 유일한 결과물입니다.


취약점 발견 못했을 경우?
- 보고서에 수행한 작업에 대한 기술적인 세부 정보를 너무 많이 포함하지 않아야 함.
- 취약점이 발견되지 않았다고 단순하게 알려줘도 됨


보고서 작성 시
- 해당 보고서를 받는 사람이 누구인지 인지하기
- 기술적 세부 사항으로 인해 과부하가 발생하지 않으면서 발견된 취약점을 정확하게 보고하는 방식으로 참여의 결과와 영향을 강조하는 섹션을 제공해야 합니다.
- 우리가 고려할 두 번째 청중은 보고서를 이해하고 식별된 취약점에 대해 설명된 해결 방법을 구현할 수 있는 기술적 지식을 갖춘 기술 직원으로 구성됩니다. 이 청중에게는 무엇이 잘못되었는지, 각 결과가 어떤 영향을 미치는지, 해결 방법을 이해할 수 있도록 충분한 기술적 세부 정보가 제공되어야 합니다. 또한 향후 유사한 유형의 문제가 발생하지 않도록 방지하는 방법에 대한 조언을 제공할 수 있을 때 이 청중은 큰 혜택을 받습니다.
